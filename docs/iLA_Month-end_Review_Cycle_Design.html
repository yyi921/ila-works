The month-end review cycle

A design for iLA: a senior accountant reviews, adjusts and completes the month from the console, without going into Xero, and always sees two numbers side by side: where the accounts are now and where they will land.

What changed in version 4. Your answers to the questions are now decisions (section 12) and are written into the sections they affect. The build order is re-sequenced (section 11).
  • To post means agreed or started by a person: journals you make go straight there. Expected is iLA's estimates, until you approve them. Both are columns in the landing view.
  • Materiality is yours to set for each core check. By default, any movement over $1,000 either way is raised. You can change each check to a $ amount, a %, points, or a combination.
  • Labour (and any other stream) can be fed by several input sources, set up per organisation.
  • The management pack is the landing view by default (changeable in admin). One person approves. Anything still in Expected at lock is archived. Only admins confirm review requests.
What changed in version 3.
  • /review is about the P&L for now (balance sheet later). It runs a set of core P&L checks by default: the last full month against last month, the same month last year and budget; YTD against budget; COGS %, labour %, EBITDA % and net profit %. Each one can be switched off in admin.
  • On top of those, you add review requests (RR-01, RR-02, …) in admin. Each one starts as a plain-English prompt. iLA turns it into a saved check, you trial run it on the last 1 or 2 months, and you confirm it once you're happy. From then on it runs every time anyone types /review.
  • /review = the core checks + every confirmed review request. Each request's result appears exactly as it looked in its trial run.
  • Event recovery % is no longer a built-in check. It becomes TECC's own review request (section 5).
What changed in version 2.
  • Findings are /review: a hybrid iLA + human review of the P&L analytics, COGS %, event recovery % and any focus areas defined in admin, which is where iLA aims its intelligence.
  • Decide is about actions (/accrue, /tag, /reclass, …) that put overlay journals into Expected or To post.
  • Two buckets in order: Expected (an estimate by iLA or you, not confirmed) → approved → To post → stamped as posted → out of both buckets. Posting and refreshing Xero start the next cycle.
  • Approving, adjusting and rejecting overlay journals live in /status, which also gets cash and the bank reconciliation status (missing today, see section 7).

Where this starts from

  • Payroll is run by The Ville and arrives in Xero as fortnightly manual journals, e.g. "Ville for TECC Payroll Journal FNE: 12/07/2026", across the labour accounts: 6345 event staff, 6300 annual leave, 6335 payroll tax, 6370 super, 6380 Workcover, 6344 bonus.
  • Month-end labour accruals are typed by hand into 2000, e.g. "Salary accrual for Oct-25 20-10 to 31-10".
  • The accrual engine already keeps payroll in its own section, but doesn't accrue it yet.
  • /status today: with no period it shows cash at bank and a count of Xero transactions not yet reconciled; with a period (/status --Oct 2026) it shows only budget and last-year measures, with no cash or bank at all. Neither shows the bank reconciliation status from /reconcile.

StepWhat happens
Into ExpectediLA's estimate from an action. It counts in the landing straight away, in the Expected column, so you always know it's iLA's number and not yet agreed.

Expected → To postOne person approves it (in /status). Still in the landing, now in the To post column.
To post → stamped as postedThe import file is built and stamped; once a person has imported it into Xero, it's marked posted. It stays counted in the layer until the next refresh finds it in Xero (by the ADJ number in the narration, or its lines), so the landing never dips between posting and refreshing. Then it leaves the buckets. That is what stops double counting.
Rejected or withdrawnLeaves the buckets, kept with its reason; the reason can become a rule.
SupersededThe real thing arrived before it was posted (the bill came in, or you posted your own accrual in Xero). iLA links it to the overlay journal with the same linker the reconciliation uses, takes it out of the buckets and shows how far the estimate was out.

Overlay journals that reverse do so in the layer next month, as Xero's auto-reversing journals do, so November isn't distorted by October's estimates.

4The cycle: refresh → review → act → view, until the month is locked

1Refreshautomatic / reread

Copy Xero (incremental). Overlay journals now found in Xero leave the buckets.

2Review/review

iLA + human review of the P&L: the core checks plus your review requests from admin.

3Act/accrue · /tag · /reclass · /reconcile · /adj

Actions put overlay journals into Expected (or straight into To post).

4View & approve/status · /pl --landing

See the new landing; approve Expected → To post; build, import and stamp what's to post.

↺ once posted journals are in Xero, the next refresh starts the next cycle
Lock the month — a snapshot of Xero's TB, the layer, the decisions, who locked it and when. Anything still in Expected is archived: you can view it, but it has no bearing anywhere in the console.

Lock

Locking needs:

  • every finding in /review reviewed (core checks and review requests)
  • every account reconciled and signed
  • the To post bucket empty (all found in Xero), or deliberately carried to next month

If Xero changes for a locked month later, iLA flags it, with the amount.

All on the landing figures (Xero + the layer), for the most recent full month unless you give a period.

  • Each check has an on/off switch and a materiality you set. The default is any movement over $1,000, either way. For each check you can change it to an amount ($), a percentage (%), points (for the ratios), or a combination (e.g. "over $1,000 and over 5%", or "over $5,000 or over 10%"). Below materiality nothing is raised, which keeps the list short.
  • With no period, /review looks at the last full month.
  • EBITDA = net profit + interest + tax + depreciation and amortisation. Which accounts count as COGS, labour, interest, tax, depreciation and amortisation is taken from Xero's account types and can be changed in admin. TECC: labour = 6300–6380.
  • iLA doesn't just list the variances. It explains each one from what it can see: the bill or journal behind it, the overlay journals in the layer, events held this month against last year, and your notes on the same line in earlier months ("Oct is always high: PBR").
  • Ad-hoc events you tell iLA once, as a note on the month or on a review request ("one-off legal fee in Oct, 12k"). iLA then treats that variance as explained, this month and when Oct is "last year" next year.

How a request becomes a check

1Writeadmin

Type the request in plain English.

2Trial runbutton

iLA turns the request into a saved check and runs it on the last 1–2 months. The result shows on the admin page.

3Adjustedit the prompt

Not quite right? Reword it ("only over $500", "group by customer") and trial run again.

4Confirm & savebutton

An admin confirms. The check is frozen and every /review runs it from now on.

  • The check is saved, not re-interpreted each time. The LLM is used once, at the trial run, to turn the prompt into a check made from iLA's own building blocks: which lines (accounts, account types, contacts, dimensions, references), which months, what to compare, what condition makes it a finding, and which columns to show. After that, code runs the saved check, so every /review gives the same kind of answer, quickly and without cost.
  • If iLA can't do it, it says so at the trial run instead of guessing: "I can't see rosters, so I can't check hours; I can check labour cost per event."
  • Change the prompt any time: it goes back to Trial run, and the confirmed version keeps running until you confirm the new one. Delete or switch it off any time.
  • A request can carry its own materiality and an action: e.g. RR-01's findings open /tag.

8Making the review intelligent

For every check and line: an expected figure, with a reason, compared against the landing. Code works out every amount; the LLM explains, drafts journals from plain English, and suggests where rules run out.

1 · Coverage, not averages

For each cost stream, which days, events or bills of the month are covered by actuals, and the gaps:

  • labour: covered by fortnightly pay runs
  • utilities: covered by each bill's service period, read from the PDF
  • event costs: covered by each event's bills

2 · Drivers

Event staff, security, cleaning and first aid scale with the events held; iLA has the Event dimension and the recovery lines on sales invoices, so the expectation is events × the usual cost per event.

3 · Ratios that should hold

The core ratios (COGS %, labour %, EBITDA %, net profit %) and any in your review requests: recovery %, GP % by event, super ÷ salaries, on-cost rates. A broken ratio is a finding with the gap worked out and the likely cause named.

4 · Evidence beats estimates, automatically

When the evidence arrives (the next pay journal, the bill, the stock journal), the Expected figure is replaced by the evidenced one, or the overlay journal is superseded, and the review says so.

5 · Learning

  • A rejection or note with a reason becomes a rule.
  • Each estimate is compared with what actually arrived; that sets each stream's accuracy, and accuracy decides how much attention it needs.

6 · Plain English

From /adj or inside a review: iLA drafts the overlay journal, shows the lines and waits for your OK.
